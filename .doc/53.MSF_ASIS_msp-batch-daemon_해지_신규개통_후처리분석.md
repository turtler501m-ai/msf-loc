# AS-IS msp-batch-daemon 해지/신규개통 후처리 분석

- 분석일: 2026-04-29
- AS-IS 배치 소스: `C:\MSF-LOC\workspace\msp-batch-daemon\trunk`
- 관련 TOBE/API 참고 소스: `C:\MSF-LOC\workspace\msf-be-form-api`
- 문서 목적: 해지 또는 신규개통 처리 이후 AS-IS `msp-batch-daemon`에서 데몬/스케줄러로 후처리하는 로직을 TOBE 이관 관점에서 정리한다.

## 1. 결론 요약

AS-IS `msp-batch-daemon`에서 확인되는 후처리는 크게 두 축이다.

1. 신규개통 후처리
   - 핵심 스케줄: `MplatformOpenRequestSchedule`
   - 트리거: `MCP_REQUEST_OSST@DL_MCP`에 `PRGR_STAT_CD = 'OP2'`이고 `RSLT_CD IN ('0000', '3060', '3070')`인 개통 성공/준성공 결과
   - 후처리: `MCP_REQUEST@DL_MCP` 상태를 개통완료(`REQUEST_STATE_CODE = '21'`)로 변경하고, `MCP_REQUEST*` 신청 데이터를 `MSP_REQUEST*` 테이블로 복사한 뒤
      `MSP_REQUEST_DTL`, `MSP_JUO_SUB_INFO`를 계약 기준으로 현행화한다.

2. 해지 후처리
   - 핵심 스케줄: `CancelSchedule`
   - 트리거: `PPS_CAN_USR_MST.PROC_STATUS = 'R'`
   - 후처리: M-Platform에 `appEventCd = 'CP0'`로 해지 연동을 호출하고, 결과에 따라 `PPS_CAN_USR_MST.PROC_STATUS`를 성공(`S`) 또는 오류(`E`)로 갱신한 뒤 `P_PPS_CAN_USR_RES` 프로시저를 호출한다.

중요한 차이점은 해지 신청 API에서 생성되는 `MCP_CANCEL_REQUEST@DL_MCP`를 `msp-batch-daemon`이 직접 폴링하는 로직은 현재 분석 범위에서 확인되지 않았다는 점이다. AS-IS 배치의 해지성 데몬 처리는 `PPS_CAN_USR_MST` 기반의 직권해지 흐름이다.

### 3.2 대상 조회 조건

SQL: `MplatformOpenMapper.getOpenCntrList`

주요 조건:

```sql
FROM MCP_REQUEST_OSST@DL_MCP A,
     MCP_REQUEST@DL_MCP B,
     MCP_REQUEST_CSTMR@DL_MCP C,
     MSP_JUO_SUB_INFO D
WHERE A.PRGR_STAT_CD = 'OP2'
  AND A.RSLT_CD IN ('0000', '3060', '3070')
  AND TO_NUMBER(A.MVNO_ORD_NO) = B.RES_NO
  AND B.REQUEST_KEY = C.REQUEST_KEY
  AND A.SVC_CNTR_NO = D.CONTRACT_NUM
  AND (D.SCAN_ID IS NULL OR D.SRL_IF_ID = 0)
```

의미:

- OSST/M-Platform 개통 결과가 `OP2`로 수신되어야 한다.
- 결과코드는 `0000`, `3060`, `3070`을 처리 대상으로 본다.
- OSST 주문번호(`MVNO_ORD_NO`)와 MCP 신청 예약번호(`RES_NO`)를 매칭한다.
- 계약번호(`SVC_CNTR_NO`)가 `MSP_JUO_SUB_INFO.CONTRACT_NUM`과 매칭되어야 한다.
- `MSP_JUO_SUB_INFO`가 아직 OSST 개통 결과로 현행화되지 않은 건만 처리한다.

### 5.2 대상 조회 조건

SQL: `CanMgmtMapper.getCanMgmtList`

```sql
SELECT CONTRACT_NUM,
       CUSTOMER_ID,
       SUBSCRIBER_NO
FROM (
    SELECT CONTRACT_NUM,
           CUSTOMER_ID,
           SUBSCRIBER_NO
    FROM PPS_CAN_USR_MST
    WHERE PROC_STATUS = 'R'
    ORDER BY REGST_DTTM ASC
)
WHERE ROWNUM <= (
    SELECT ETC1
    FROM CMN_GRP_CD_MST
    WHERE GRP_ID = 'DEV0000'
      AND CD_VAL = 'LIMIT'
)
```

의미:

- 처리대기 상태는 `PROC_STATUS = 'R'`이다.
- 오래 등록된 순으로 처리한다.
- 처리 건수 제한은 공통코드 `CMN_GRP_CD_MST(GRP_ID='DEV0000', CD_VAL='LIMIT')`의 `ETC1` 값을 사용한다.

### 5.3 M-Platform 호출 파라미터

```java
paramMap.put("ncn", vo.getContractNum());
```

의미:

### 5.4 결과 반영

M-Platform 호출 결과가 `SUCCESS`이면:

- `PPS_CAN_USR_MST.PROC_STATUS = 'S'`
- `CONN_RSLT_KEY`, `CONN_RSLT_TYPE`, `CONN_RSLT_CD`, `CONN_RSLT_MSG`를 저장
- `PROC_DTTM = SYSDATE`

실패이면:

- `PPS_CAN_USR_MST.PROC_STATUS = 'E'`
- `PROC_DESC = result`
- `PROC_DTTM = SYSDATE`

그 뒤 공통으로 다음 프로시저를 호출한다.

```sql
    contractNum,
    customerId,
    connRsltKey,
    connRsltType,
    connRsltCd,
    connRsltMsg,
    '',
    '',
    ''
)
```

## 6. MSF 해지 신청 API와 daemon 해지 배치의 연결성

TOBE/API 쪽 해지 신청 처리에서는 다음 흐름이 확인된다.

- `MsfCancelPageSvcImpl.complete()`
- `apply()`
- `MSF_REQUEST_CANCEL` 저장
- `MSF_REQUEST_CSTMR` 저장
- `MCP_REQUEST_CSTMR@DL_MCP` 저장
- `MCP_CANCEL_REQUEST@DL_MCP` 저장

해지 신청 데이터의 주요 값:

- `OPER_TYPE_CD = 'CC'`
- `PROC_CD = 'RC'`
- `REGST_ID = 'MSF_FORM'`
- `REC_YN = 'N'`
- `APP_FORM_YN = 'N'`
- `APP_FORM_XML_YN = 'N'`

그러나 `msp-batch-daemon`의 `trunk/src/main/java`, `trunk/src/main/resources/sqlmap` 범위에서 `MCP_CANCEL_REQUEST`를 직접 조회하거나 `PROC_CD = 'RC'/'RQ'`를 폴링하는 스케줄은 확인되지 않았다.

따라서 현재 소스 기준 판단은 다음과 같다.

- `MCP_CANCEL_REQUEST@DL_MCP`는 해지 신청/접수 데이터 저장 경로이다.
- `msp-batch-daemon`의 즉시성 해지 데몬은 `PPS_CAN_USR_MST`의 `PROC_STATUS = 'R'` 데이터를 처리한다.
- 신청 해지(`MCP_CANCEL_REQUEST`)와 직권해지(`PPS_CAN_USR_MST`)는 같은 “해지” 도메인으로 보이지만, 배치 트리거와 테이블이 다르다.
- TOBE에서 “해지 신청 후 daemon 후처리”를 그대로 구현하려면, AS-IS에 없는 `MCP_CANCEL_REQUEST` 폴링 배치를 새로 만들 것인지, 기존처럼 관리자/외부 프로세스가 별도 상태 전이를 수행하는지 먼저 확정해야 한다.

## 7. 개통 후 LMS 등 부가 후처리

`OpenCstmrLmsSchedule`은 개통고객 LMS 발송 후속 배치이다.

- 스케줄: `openCstmrLmsSchedule = 0 3/5 10-21 * * ?`
- 서비스: `OpenCstmrLmsService.setOpenCstmrLms()`
- SQL: `OpenMgmt_SQL.xml`
- 주요 테이블: `MSP_RATE_CANCEL_LMS`, `MSP_SMS_SEND_MST` 계열

이 로직은 개통 결과 자체를 MSP 신청/계약정보에 반영하는 핵심 후처리라기보다, 개통된 고객에게 할인/위약금 안내성 LMS를 생성하고 발송 상태를 관리하는 후속 업무로 분류하는 것이 맞다.

## 8. TOBE 이관 시 반영 포인트

### 8.1 신규개통 후처리

TOBE에서 AS-IS와 동일한 의미를 유지하려면 다음 단위가 필요하다.

1. OSST/M-Platform 결과 수신 또는 조회 저장
   - `MCP_REQUEST_OSST`에 해당하는 결과 저장소가 필요하다.
   - 최소 상태값: `PRGR_STAT_CD`, `RSLT_CD`, `MVNO_ORD_NO`, `SVC_CNTR_NO`, `SEQ`.

2. 개통완료 대상 조회
   - 조건은 AS-IS 기준 `OP2 + RSLT_CD IN ('0000','3060','3070')`이다.
   - 중복 처리 방지를 위해 `MSP_JUO_SUB_INFO.SCAN_ID IS NULL OR SRL_IF_ID = 0`에 해당하는 TOBE 조건이 필요하다.

3. 신청정보 복사/스냅샷 생성
   - `MCP_REQUEST* -> MSP_REQUEST*` 복사 의미를 TOBE 구조에서 재정의해야 한다.
   - TOBE가 신청 원장과 업무 원장을 분리하지 않는다면 복사 대신 상태 전이/스냅샷 테이블 저장으로 대체할 수 있다.

4. 계약현행화
   - `MSP_REQUEST_DTL`과 `MSP_JUO_SUB_INFO`에 해당하는 계약 상세/가입자 현행 테이블 갱신이 핵심이다.
   - 개통 후 화면/업무가 참조하는 기준 테이블이 무엇인지 먼저 확정해야 한다.

5. 실패/미개통 삭제
   - 직접개통 미완료 건 삭제 정책은 운영 리스크가 크므로 TOBE에서는 물리삭제보다 상태값 마킹 또는 보관 후 삭제 정책을 검토하는 것이 안전하다.

### 8.2 해지 후처리

AS-IS와 동일하게 가려면 다음 단위가 필요하다.

1. 처리대기 큐
   - AS-IS는 `PPS_CAN_USR_MST.PROC_STATUS = 'R'`가 큐 역할을 한다.
   - TOBE에서 해지 신청 테이블을 큐로 사용할지, 별도 해지 연동 큐 테이블을 둘지 결정해야 한다.

2. M-Platform 해지 연동
   - 이벤트 코드: `CP0`
   - 필수 파라미터: 가입자번호(`ctn`), 계약번호(`ncn`), 고객ID(`custId`)

3. 결과 저장
   - 성공: `S`, 실패: `E`
   - 연동 결과키/타입/코드/메시지를 저장해야 재처리와 장애 추적이 가능하다.

4. 후속 프로시저 대체
   - AS-IS는 `P_PPS_CAN_USR_RES('CONN', ...)`로 후속 처리를 위임한다.
   - TOBE에서는 이 프로시저 내부 역할을 확인해 Java 서비스/DB 프로시저/이벤트 발행 중 하나로 대체해야 한다.

## 11. 남은 확인 필요 사항

1. `P_PPS_CAN_USR_RES` 프로시저 내부 로직
   - DB 프로시저라 Java 소스에는 구현이 없다.
   - 해지 후 실제 어떤 테이블을 갱신하고 어떤 시스템으로 전파하는지 DB에서 확인해야 한다.

2. `MCP_CANCEL_REQUEST@DL_MCP` 후속 처리 주체
   - `msp-batch-daemon`에서는 직접 폴링 배치가 확인되지 않았다.
   - 관리자 화면, 다른 데몬, DB 프로시저, 외부 시스템 중 어디서 `PROC_CD`를 전이하는지 추가 확인이 필요하다.

3. OSST 결과코드 `3060`, `3070`의 정확한 업무 의미
   - AS-IS는 성공성 코드로 처리하지만, 코드명/정책은 운영 코드표 또는 M-Platform 인터페이스 문서에서 확인해야 한다.
