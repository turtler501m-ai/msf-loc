## 3. 실행 진입점 — BatchLoader.java

```
실행 인자 (args):
  [0] batch.server.type    — local | dev | live
  [1] batch.run.type       — schedule | onetime | test
  [2] batch.load.package   — bnd | cls | org | ptnr | rcp ...
  [3] 스케줄러 Bean 이름    — BondSchedule, SmsRsvSendSchedule ...
  [4] 실행 파라미터         — (선택)
```

**launch 설정 파일 3종**

| 파일 | 용도 | 주요 설정 |
|------|------|----------|
| `launch-context.xml` | 스케줄 모드 | `@Scheduled` 활성, TaskScheduler pool=100 |
| `launch-manager-context.xml` | 원타임(수동) 실행 | 스케줄러 비활성 |
| `launch-context-test.xml` | 테스트 | 테스트 프로파일 |

## 4. 배치 실행 흐름

```
@Scheduled(cron="${xxxSchedule}")
    │
    ▼
BaseSchedule.batchStart()     ← BATCH_EXEC_HST 상태 = ING
    │
    ▼
Service.xxx()                  ← 비즈니스 로직 + Mapper 호출
    │
    ├── 성공 → BaseSchedule.batchEnd()    ← 상태 = END
    └── 실패 → BaseSchedule.batchError() ← 상태 = ERR, 에러메시지 저장
```

## 12. MSF 신규 스마트서식지 — 개통·명의변경·해지 KOS 연계 후처리 분析

### 12.1 개요

스마트서식지(MSF)에서 개통·명의변경·서비스해지 신청 완료 후 KOS(KT Operating System)까지 도달하는 처리 경로는 도메인별로 다르다.

| 도메인 | KOS 경로 | API 호출 주체 | TOBE 구현 상태 |
|--------|---------|-------------|--------------|
| 신규가입(개통) | MSF → M플랫폼 OSST → KOS | 배치 (MSP 기존) | 기존 MSP 배치 활용 |
| 명의변경 | MSF → M포탈 → M플랫폼 → KOS | 배치 예정 | 미구현 |
| 서비스해지 | MSF → M포탈 적재 → MSP 담당자 → M플랫폼 → KOS | MSF 직접 + 배치 동기화 | 진행 중 |
| 직권해지 | PPS DB → MSP 배치 → M플랫폼 → KOS | MSP 배치 | 기존 MSP 활용 |

---

### 12.2 서비스해지 KOS 연계 후처리 흐름

#### 처리 단계별 순서 (T0 ~ T3)

```
T0: MSF App 신청 완료
    ├─ MSF_REQUEST_CANCEL INSERT  (PROC_CD='RC')
    └─ requestKey 발급

T1: M포탈 적재  [MsfCancelPageSvcImpl.apply()]
    ├─ POST /mcp/api/cancel/msf-register
    │   요청: { contractNum, cstmrName, payAmt, pnltAmt, lastSumAmt, ... }
    │   M포탈 INSERT: NMCP_CUST_REQUEST_MST, MCP_CANCEL_REQUEST
    │   응답: custReqSeq (YYYYMMDD+5자리)
    │   → MSF_REQUEST_CANCEL.RES_NO UPDATE
    │
    ├─ SCAN 서버 전송  [FormCommRestSvc.sendScan]
    │   XML 생성 (CANCEL_MOBILE_NO, CONTRACT_NUM, PAY_AMT, PNLT_AMT, ...)
    │   FTP 업로드
    │   → MSF_REQUEST_CANCEL.SCAN_ID UPDATE
    │
    └─ POST /mcp/api/cancel/update-scan
        { custReqSeq, scanId }
        → MCP_CANCEL_REQUEST.SCAN_ID UPDATE

T2: MSP 담당자 처리
    ├─ 해지상담 목록 조회
    │   CanCustMgmt_SQL.xml  selectCanCslListInfo
    │   FROM MCP_CANCEL_REQUEST@DL_MCP A
    │        LEFT JOIN MSP_REQUEST_DTL C
    ├─ 처리 확정: PROC_CD='CP'
    │   UPDATE MCP_CANCEL_REQUEST@DL_MCP SET PROC_CD='CP'
    └─ M플랫폼 자동 → KOS 실제 해지 처리

T3: MSF 배치 동기화  [SvcCnclSyncBatch — 6시간 주기, 미구현]
    ├─ SELECT REQUEST_KEY, RES_NO
    │   FROM MSF_REQUEST_CANCEL WHERE PROC_CD='RC'
    ├─ 방안 A (RES_NO 있을 때)
    │   POST /mcp/api/cancel/status-batch { custReqSeqs:[...] }
    │   → PROC_CD='CP' 건 UPDATE
    └─ 방안 B (RES_NO 없을 때)
        X01 perMyktfInfo() → ACNT_STAT='C' 확인
        → PROC_CD='CP' UPDATE
```

#### PROC_CD 상태값

| 코드 | 상태 | 생성 주체 | 설명 |
|------|------|---------|------|
| `RC` | 접수 | MSF App | 신청서 저장 직후 |
| `CP` | 처리완료 | MSP 담당자 또는 배치 | MSP 확정 또는 배치 동기화 |
| `BK` | 백업(삭제) | MCP 배치 | 6개월 미처리 건 자동 삭제 |

#### 관련 테이블

| 테이블 | 위치 | 주요 컬럼 |
|--------|------|---------|
| `MSF_REQUEST_CANCEL` | MSF DB | `REQUEST_KEY`, `PROC_CD`, `RES_NO`, `SCAN_ID`, `PAY_AMT`, `PNLT_AMT`, `LAST_SUM_AMT` |
| `MSF_REQUEST_CSTMR` | MSF DB | `REQUEST_KEY`(FK), `CSTMR_NM`, `CSTMR_NATIVE_BIRTH`, `CSTMR_MOBILE_FN_NO` |
| `MCP_CANCEL_REQUEST` | M포탈 (@DL_MCP) | `CUST_REQ_SEQ`, `REGST_ID='MFORM'`, `ONLINE_AUTH_INFO='MSF:{requestKey}'`, `PROC_CD`, `SCAN_ID` |
| `NMCP_CUST_REQUEST_MST` | M포탈 (@DL_MCP) | `REQ_TYPE='CC'`, `USERID='MFORM'` |
| `MSP_JUO_SUB_INFO` | MSP | `CONTRACT_NUM` (조인 키) |

### 12.3 신규가입(개통) KOS 연계 후처리 흐름

#### 처리 경로

```
MSF 신청 완료
    │
    ▼
[MSP 배치] OsstMgmtService.selectNonOsstRcpList()
    ├─ FROM MCP_REQUEST@DL_MCP
    │       MSP_JUO_SUB_INFO
    ├─ WHERE REQUEST_STATE_CODE != '21'  (미개통)
    └─ 약 100건 단위 처리
         │
         ▼
    MplatFormService.callService(paramMap)
         ├─ M플랫폼 OSST API (HTTP POST)
         └─ appEventCd별 분기
              │
              ▼
         KOS 실제 처리
```

#### OSST appEventCd 목록

|-----------|--------|------|

### 13.3 setMplatformOpenRetry() — 전일 미개통 재처리

전일 번호예약 후 개통 못한 건을 다음날 재처리한다.

```
getMplatformOpenRetryList()    ← 전일 미개통 재처리 대상 조회
    │
    └─ 건별 Loop
         │
         ├─ [1단계] setRequestCopy()       신청서 전체 복사 (12개 테이블)
         │           oldRequestKey → 신규 requestKey 생성
         │
         ├─ [2단계] appEventCd="PC0"       사전체크 전송
         │           osstServiceCall(reqVO)
         │
         ├─ sleep(30초)                     TCP 결과수신 대기
         │
         └─ [3단계] while(!tcpRslt) — 최대 3회 재시도
                    │
                    ├─ appEventCd="PC2"    TCP 결과 확인
                    │   getTcpResult(reqVO)
                    │
                    ├─ 성공 (rtnChk > 0)
                    │   ├─ appEventCd="NU2", gubun="RSV"  번호예약이력 생성
                    │   ├─ insertRequestOsstHist()
                    │   └─ osstServiceCall()               번호예약 전송
                    │
                    └─ 실패 (tryCnt < 3)
                        └─ sleep(30초) → 재시도
                           3회 초과 시 PASS (skip)
```

**재시도 타임라인:**
```
PC0 송신 → [30초] → PC2 확인
              실패  → [30초] → PC2 확인
              실패  → [30초] → PC2 확인
              실패  → PASS  (최대 120초 소요)
```

## 14. TmntPpImgTransferSchedule.java 상세 분析

### 14.1 목적

**해지 후 180일 경과한 선불(PP) 고객의 서식지 이미지 파일을 운영 NAS에서 아카이브 NAS로 이관**한다.

- 대상: 선불(PPPO ≠ 'PO') 해지고객 중 `PPS_CUSTOMER_IMAGE.IMG_PATH`가 `/jboss/data/` 경로인 건
- 이관 방향: `/jboss/data/` (운영 NAS) → `/jboss/data_can/` (아카이브 NAS)
- 1회 처리량: 최대 180건 (ROWNUM <= 180)

> 2025-10-23: 백업 NAS 경로 변경 `/jboss/data2/` → `/jboss/data_can/`

### 14.2 전체 처리 흐름

```

    │   FROM MSP_JUO_SUB_INFO@DL_CAN
    │   WHERE TRANSFER_DTTM <= 오늘
    │     AND PPPO <> 'PO'  (선불)

    │           WHERE IMG_PATH LIKE '/jboss/data/%' AND STATUS='A'

              ├─ [3단계] 경로 계산
              │   AS-IS: /jboss/data/webscan/prd/image/ORIGIN_DIR/E0001/2017/07/27/xxx.JPG
              │   TO-BE: /jboss/data_can/webscan/prd/image/ORIGIN_DIR/E0001/2017/07/27/xxx.JPG
              │   (파일명 '?' → '_' 치환)
              │
              ├─ [4단계] TO-BE 디렉토리 생성 (없으면 mkdirs())
              │
              ├─ [5단계] 파일 이동
              │   AS-IS 파일 존재 → FileInputStream → FileOutputStream → AS-IS 삭제
              │   AS-IS 파일 없음 → skip (로그만)
              │
              ├─ [6단계] STATUS 결정
              │   TO-BE 파일 존재 → status = 'A'
              │   TO-BE 파일 없음 → status = 'D'
              │
              ├─ [7단계] MSP DB 경로 업데이트
              │   updateMspPpsCustomerImage()
              │   UPDATE PPS_CUSTOMER_IMAGE SET IMG_PATH=tobeFileInfo, STATUS=status
              │   WHERE IMG_SEQ = #{imgSeq}
              │
              └─ [8단계] CAN DB INSERT/UPDATE
                  chkCanPpsCustomerImage()  — COUNT(*) FROM PPS_CUSTOMER_IMAGE@DL_CAN
                  = 0 → insertCanPpsCustomerImage()
                  > 0 → updateCanPpsCustomerImage()
                  (SELECT ... FROM PPS_CUSTOMER_IMAGE WHERE IMG_SEQ = #{imgSeq})
```

## 15. 해지(EP0) 후처리 — 해지 고객 데이터 생명주기 관리

### 15.1 EP0 이벤트 코드 개요

`EP0`는 KOS(KT 운용 시스템)가 서비스해지 완료를 M플랫폼에 통보하는 OSST 이벤트 코드다.  
`msp-batch-daemon` 소스 내에는 `EP0` 문자열이 직접 등장하지 않는다.  
그 이유는 해지 완료 이후 **배치 처리 대상**이 되는 고객 데이터의 생명주기 관리가  
`CanTransferService.java` 및 관련 스케줄러에 완전히 위임되어 있기 때문이다.

> **정리**: EP0 이벤트 수신 → MSP DB에 해지 상태 기록 → 이후 배치가 경과일 기준으로 이관·삭제 처리

---

### 15.2 해지 고객 데이터 생명주기

```
서비스해지 완료(EP0)
       │
       ▼
  [T+0] MSP DB에 해지 기록 (MSP_JUO_SUB_INFO.ST_CD = '30' 등)
       │
       ▼ 60일 경과
  [T+60] 미개통 신청정보 삭제 (procReqCustNotOpen)
       │           ← 개통 안 된 신청서 DB 13개 테이블 삭제
       ▼ 180일 경과
  [T+180] 해지고객 이관 (procTmntCustTransfer)
       │           ← MSP → @DL_CAN 30+ 테이블 INSERT
       │           ← NAS /jboss/data/ → /jboss/data_can/ 파일 이동
       │           ← KT 현행화 테이블(JUO_SUB_INFO 등) 이관
       │           ← 단말보험/TOSS/OSST 오더 이관
       ▼ 1825일(5년) 경과
  [T+1825] 최종 삭제 (deleteTmntCustData)
               ← MCP + MSP + CAN 3개 DB 전체 테이블 DELETE
               ← 선불 테이블(PPS_*) 포함
```

---

### 15.3 주요 상수 (CanTransferService.java)

| 상수명 | 값 | 비고 |
|--------|-----|------|
| `NOT_OPEN_DT` | 60 | 미개통 신청정보 삭제 기준일 |
| `TMNT_CUST_DT` | 180 | 해지고객 이관 기준일 |
| `TMNT_CUST_DEL_DT` | 1825 | 해지고객 최종삭제 기준일 (5년) |

### 15.6 procTmntCustTransfer() — 180일 해지고객 이관

**목적**: 해지 후 180일 경과 고객의 MSP 데이터를 CAN(아카이브 DB)으로 이관

**주요 처리 단계**:

1. **이관 대상 조회** — `MSP_JUO_SUB_INFO`에서 해지일 180일 경과 고객 목록 조회
2. **MSP → @DL_CAN 이관** — 30개 이상 테이블 INSERT INTO ... SELECT ... FROM ... (DB Link 경유)
3. **KT 현행화 테이블 처리**:
   - `JUO_SUB_INFO` — 계약 현행화 정보
   - `JUO_CUS_INFO` — 고객 기본 정보
   - `JUO_BAN_INFO` — 제재/차단 정보
4. **단말보험 이관** — `MSP_INTM_INSR_MST` → `@DL_CAN`
5. **보상서비스 이관** — 보상 관련 테이블
6. **TOSS 결제정보 이관** — `TOSS_*` 테이블
7. **OSST 오더 이관** — `MSP_OSST_ORDER` → `@DL_CAN`
8. **NAS 파일 이동** — `/jboss/data/` → `/jboss/data_can/` (2025-10-23 변경)
9. **개인정보 치환** — 이관 후 원본 테이블 개인정보 마스킹
10. **MSP 원본 삭제** — 이관 완료된 MSP 레코드 DELETE

**강제종료 플래그**: `CAN_TRANS_STOP` — DB에서 값 읽어 배치 긴급 정지 가능

**트랜잭션**: 고객 단위 `@Transactional(rollbackFor=Exception.class)` — 한 건 오류 시 해당 고객만 롤백, 전체 배치 계속 진행

### 15.7 deleteTmntCustData() — 1825일 최종 삭제

**삭제 DB 범위**:

**선불 테이블 삭제 대상**: `PPS_CUSTOMER`, `PPS_CUSTOMER_IMAGE`, `PPS_CHARGE_HIST` 등

### 15.11 MSF TOBE 관련성

| 항목 | 내용 |
|------|------|
| **EP0 수신 처리** | MSF가 해지 완료(EP0) OSST 이벤트를 수신하면 `MSF_REQUEST_CANCEL` 테이블에 해지 완료 상태 기록 필요 |
