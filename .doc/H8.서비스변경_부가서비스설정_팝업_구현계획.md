> ※ PPTX 설계서(v1.0_20260422) 기준으로 상품코드 분류 재정정 — `LTEDTROM5`와 `DYDTROM05` 배치가 기존 H7 분석과 반대임

| variant | 퍼블 | 대상 상품코드 | UI |

## 4. isSettingButtonDisabled 수정

### 현재

```javascript
// 기존 이용중 서비스는 illegalTm만 설정 가능
if (isExistingService(svc)) {
  return modalType !== 'illegalTm'
}
```

### 변경 후

기존 서비스에서 설정 변경 허용할 유형:
- `illegalTm` (NOSPAM4): ✅ 허용
- `blockNumber100` (NOSPAM2): ✅ 허용 (차단번호 변경)
- `infoProviderBlock` (NOSPAM3): ✅ 허용 (차단번호 변경)
- `autoRing` 계열: ✅ 허용 (장르 변경)
- 로밍 계열: ❌ 비허용 (기존 가입 서비스는 로밍 날짜 재설정 불가)
- `numberSpoofing`: ❌ 비허용 (기존 이용중이면 이미 동의 완료)

```javascript
const EXISTING_SERVICE_SETTABLE = new Set([
  'illegalTm', 'blockNumber100', 'infoProviderBlock',
])

const isSettingButtonDisabled = (svc = {}) => {
  const modalType = getSettingModalType(svc)
  if (!modalType || modalType === 'autoDefault') return true
  if (isExistingService(svc)) {
    return !EXISTING_SERVICE_SETTABLE.has(modalType)
  }
  return false
}
```

## 5. autoDefault 처리 (ITCRBS + 오토링 계열)

`getSettingModalType`이 `'autoDefault'`를 반환하는 상품은  
팝업 없이 가입 즉시 `addSvcSettingCompleted = true` 자동 처리.

`MsfServiceChangeAdditon.vue` → `onVasConfirm` 또는 `syncSelectedServices`에서  
`autoDefault` 유형 서비스는 추가 시 자동으로 설정 완료 처리.

| 상품코드 | 상품명 | 자동처리 값 |
|---|---|---|
| ITCRBS | 국제전화수신차단 | ON 고정 |
| RNGTOUPR3 | 오토링 | `GENRE=*` (기본값 0=추천) |
| SKCOREPAC | 핵심팩 | `GENRE=*` 동일 |
| XRINGMON | 링투유 오토체인지(월) | `GENRE=*` 동일 |
| XRINGWEEK | 링투유 오토체인지(주) | `GENRE=*` 동일 |

> ※ 향후 장르 선택 팝업 추가 가능하나 현재는 디폴트(`*`)로 자동 처리

## 6. ftrNewParam 생성 규칙 (Codex 지적 반영)

### 문제

`MsfServiceChangeAdditon.vue:412`에 폴백 로직 존재:
```javascript
if (Object.keys(settingData).length > 0) return JSON.stringify(settingData) // ← 위험
```
`msf_serviceChange.js getFtrNewParam`은 `KEY=VALUE|KEY=VALUE` 형식이지만,  
모달이 `ftrNewParam`을 직접 포함하지 않으면 `JSON.stringify` 경로를 탈 수 있음 → Y25에 잘못된 값 전달.

### 규칙: 모달은 반드시 ftrNewParam 문자열을 직접 emit

```javascript
// 각 모달의 onConfirm에서 반드시 이 형식으로 emit
emit('confirm', { ftrNewParam: '계산된문자열' })

// 예시 — MsfIllegalTmBlockModal
const ftrNewParam = rows.map(r => formatBlockNumber(r)).join(':')
emit('confirm', { ftrNewParam })

// 예시 — MsfNotifyPhoneModal
emit('confirm', { ftrNewParam: phoneNumber.value })

// 예시 — MsfRoamingStartDateModal (dateTimeRange)
const ftrNewParam = `${formatDate(startDate)}${startHour}:${formatDate(endDate)}`
emit('confirm', { ftrNewParam })
```

`MsfServiceChangeAdditon.vue`의 `applySettingData`는 `settingData.ftrNewParam`을 그대로 사용하므로  
**모달이 ftrNewParam 키를 포함해서 emit하면 JSON.stringify 폴백 경로는 자동으로 건너뜀.**

## 8. MsfIllegalTmBlockModal maxCount 리팩토링 계획 (Codex 지적 반영)

현재 `MsfIllegalTmBlockModal.vue:229`에 `filledRows.length > 50` 하드코딩.  
NOSPAM2(100개) 재사용을 위해 props 추가 필요.

```javascript
const props = defineProps({
  modelValue: Boolean,
  maxCount: { type: Number, default: 50 },    // NOSPAM4=50, NOSPAM2=100
  minLength: { type: Number, default: 0 },     // NOSPAM2=3자리 이상
})

// 유효성 내부
if (filledRows.length > props.maxCount) {
  return `번호 입력 항목은 최대 ${props.maxCount}개까지 설정 가능합니다.`
}
if (props.minLength > 0 && someDigit.length < props.minLength) {
  return `${props.minLength}자리 이상 입력해 주세요.`
}
```

**MsfBlockNumber100Modal.vue는 별도 파일 생성 대신**  
`MsfIllegalTmBlockModal.vue`에 `maxCount=100` `minLength=3` props 전달로 대체 가능.
